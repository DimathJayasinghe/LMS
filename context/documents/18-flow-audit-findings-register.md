# 18 — Flow Audit Findings Register (2026-11-19)

> Output of the roles, scope and flow audit. The narrative, role matrix, journeys and Sri Lankan scenario
> status are in [17-roles-permissions-and-flows.md](./17-roles-permissions-and-flows.md); this file is the
> itemised register with a fix for each finding. **Nothing here has been fixed**: the audit changed docs only.
>
> Code is the authority. Each finding was traced to `file:line` during the audit, but that line-level evidence is
> kept in the private audit notes, not in this repository; re-locate the code from the endpoint or function named
> in the row. The *Checked* column says how far it was confirmed.
>
> | Checked | Meaning |
> |---|---|
> | `live` | Reproduced against a disposable local stack with real role logins |
> | `code` | Traced to `file:line` by one auditor; not exercised live |
> | `code + 2nd` | Also re-read by an independent second reviewer told to refute it (every finding originally rated high that was not already live-checked; outcomes in §2) |
>
> F-01 was checked in code and the cookie lifetime was observed live (`Max-Age=900`); the 15-minute logout itself
> was not replayed. Treat any `code` finding as a strong lead that needs a
> Vitest case when fixed (`04-ai-workflow-rules.md` §3.4), not as a settled fact.
>
> **Severity rubric.** *critical* = breaks the platform for essentially every user. *high* = an access leak, or it
> blocks a daily core flow (stay logged in, enroll, collect a fee, take attendance, sit an exam, mark an exam).
> *medium* = real defect or missing operating surface with a workable workaround. *low* = hygiene, drift, edge.
> **Owner?** = needs an owner decision before it can be fixed (collected in doc 17 §9).
>
> The repository is public, so security-class findings describe the defect and the fix, not a reproduction.
> IDs are stable (`F-nn`). *Source IDs* are labels from the private audit notes and can overlap by domain.

### Fix guidance

- **F-01** (critical, M) — Make the session survive access-token expiry in both the browser and server-rendered pages. Option (a), setting the access cookie maxAge longer than the JWT so the `expired:true` branch fires, fixes only client-side calls: the app layout resolves the session server-side and does not refresh, so a lapsed token still sends the user to login. Prefer (b): a frontend proxy.ts (Next middleware) that on a missing or expired access token calls POST /api/auth/refresh with the refresh cookie (widen its path to / or proxy it) and sets the new cookies; optionally combine with (a). Reproduce the 16-minute-old session live first. Also add a single-flight lock around api.ts refresh() so parallel 401s do not trigger REFRESH_TOKEN_REUSED (auth.service.ts:~238-252 revokes ALL sessions on reuse). Add an e2e test that simulates a 16-minute-old session. _Docs:_ `context/frontend/04-api-integration.md`, `context/api_endpoints/auth.endpoints.md`, `context/documents/02-architecture.md (auth section)`, `context/frontend/04-api-integration.md §6`.
